# TEE-only XRP testnet wallet

A Flare Confidential Compute (FCC) extension that generates an XRP Ledger
testnet wallet *inside* the TEE, never exports the private key, exposes its
address so anyone can fund it with test XRP, and lets anyone request a payout
of 10% of its current balance.

Built as a drop-in replacement for the `python` variant of Flare's official
`fce-sign` example (https://github.com/flare-foundation/fce-sign), which this
was verified against directly. It reuses that repo's deployment tooling,
Docker Compose stack, and `base/` framework unmodified — only the contract and
`python/app/` are different.

## What's here

```
contracts/
  XrpWalletSender.sol          replaces contracts/InstructionSender.sol
  interfaces/                  unchanged copies from the template
python/app/
  config.py                    OPType/OPCommand constants + XRPL RPC URL
  handlers.py                  wallet generation, address lookup, 10% payout
python/requirements.txt        only dependency is xrpl-py
frontend/index.html            single-file UI (MetaMask + ethers.js via CDN)
```

## How it differs from the sign-extension example

- No `UPDATE_KEY` instruction — the private key is generated by `Wallet.create()`
  inside `handlers.py` the first time it's needed. Nobody ever supplies it, so
  nobody outside the enclave ever knows it. Restarting the container therefore
  generates a **new** wallet/address — nothing is persisted outside memory.
  That's intentional: it's the clearest demonstration that only the TEE
  controls the key.
- `requestAddress()` — anyone can call this to have the TEE report its current
  XRP address (no secret is revealed, just the classic address).
- `award(bytes xrpAddress)` — anyone can call this with an XRP testnet address;
  the TEE checks its own balance via the public XRPL testnet JSON-RPC
  (`https://s.altnet.rippletest.net:51234/`), computes 10% of it, and submits
  a signed `Payment` transaction on XRPL testnet.
- The contract emits its own `InstructionSent(instructionId, ...)` event so the
  frontend can read the instruction ID straight out of the transaction
  receipt, instead of decoding the registry's internal event (whose ABI isn't
  publicly documented).

## Setup

1. Clone `fce-sign` and follow its guide through **Step 4** (chain selection,
   deployer keys, ngrok tunnel reservation, indexer DB config) with
   `LANGUAGE=python`.
2. Copy this repo's files over the template:
   - `contracts/XrpWalletSender.sol` → `contracts/` (remove/replace the
     original `InstructionSender.sol`)
   - `python/app/config.py`, `python/app/handlers.py` → `python/app/`
   - Add `xrpl-py>=3.0.0` to `python/requirements.txt`
3. Continue the template's guide from **Step 5** onward (`start-services.sh`,
   `post-build.sh`) — deployment tooling doesn't need to change.
4. Open `frontend/index.html` directly in a browser (no build step). Fill in
   the contract address (written to `config/extension.env` by `pre-build.sh`)
   and your `EXT_PROXY_URL`.

## Things I could not verify and you should check before relying on this

- **Fee amount.** The exact `msg.value` the registry requires per instruction
  isn't documented in the public guide; the Go test tooling defaults to a
  tiny placeholder (`1e-6 C2FLR`). The frontend defaults to `0.01 C2FLR` —
  adjust if calls revert.
- **CORS.** The frontend calls `${EXT_PROXY_URL}/action/result/<id>` directly
  from the browser. I confirmed this route exists (from the Go tooling
  source), but not whether the proxy sends CORS headers for browser fetches.
  If requests fail with a CORS error, you'll need a small same-origin relay.
- **Outbound network access.** `handlers.py` makes real HTTPS calls to the
  public XRPL testnet RPC from inside the `extension-tee` container. Confirm
  the container's network policy allows outbound HTTPS before deploying.
- **XRPL reserve.** Repeated `award()` calls will eventually fail (not error
  gracefully beyond the returned message) if the payout would drop the wallet
  below the XRPL testnet's minimum account reserve — kept simple on purpose,
  not handled specially.
- Only the **simulated-TEE** deployment path was covered in what I read.
  Real production TEEs (GCP Confidential Space) are a separate deployment
  path (`DEPLOYMENT_STEPS.md` in the template repo) I haven't looked at.
